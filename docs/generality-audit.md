# What in cairn is tied to the repository it was measured on

Written 2026-08-01, after a day of building against one codebase. The question is whether
anything was hand-fitted to that repository, and the honest answer has three tiers.

## Tier 1 — nothing names this company, repo or domain in production code

Every occurrence of a company, service, domain or module name from the measured repository
in the Rust source is either a doc comment recording *why* a mechanism exists, or a test
fixture. Checked by grepping all of `crates/` and separating comment and test lines from
the rest; the remainder is empty.

Those names have since been replaced throughout this repository with neutral stand-ins —
the measured codebase is closed source, and the examples read the same either way. What the
doc comments record is the shape of a problem, not whose problem it was.

The constants are all generic: the handle alphabet, timeouts, `.git`/`node_modules`/`.venv`
skip lists, generated-code markers (`code generated by`, `@generated`, `do not edit`), and
protoc path hints (`.pb.go`, `_pb2.py`).

## Tier 2 — ecosystem conventions, hardcoded, and they are the load-bearing parts

These are not specific to this repository, but they are specific to *an* ecosystem, and if
a repo does not follow them the mechanism produces nothing:

| where | assumes |
|---|---|
| `deploy::resolve_command` | `python -m`, `uvicorn`/`gunicorn`, `manage.py <cmd>`, `celery -A`, `tail -f`/`sleep infinity` |
| `deploy::binary_to_package` | a Dockerfile line building with `-o <path>` |
| `deploy` Django command | a management command is a file named `<command>.py` |
| `protolink::classify` | protoc naming: `<Svc>Base`, `<Svc>Stub`, `<Svc>Client`, `<Svc>Server`, `Register<Svc>Server` |
| `ondemand` | cron's five fields, and `docker exec … -f name=<service>` |
| `conventions` | tests live in `tests/` or are named `test_*` |

**Paid.** They are now `crates/cairn-store/src/rules/default.yaml`, embedded so a repository
following the usual conventions needs no file, and overridable by dropping a `rules.yaml`
beside the index. `cairn rules` prints the effective pack and says where it came from;
`cairn index` reports when it loaded one.

Verified two ways. Re-indexing the measured repository with the pack driving the code gives
identical numbers — 73 services, 477 serve and 321 call links, 275 generated files, 10
resolved entrypoints, 3 cron entrypoints — so the refactor changed no behaviour. And
changing one field in a copied pack (`service_marker`) takes cross-language linking to zero,
which `status` then reports as the mechanism failing rather than as an answer.

What remains hardcoded is the *shape* of a rule, not its content: the pack can say a command
is `<interpreter> -m <module>` but not invent a new kind of target. Adding a language is a
pack; adding a new way of pointing at code is still a patch.

**Paid again, differently.** The pack made the *content* of these conventions
configurable; it left them running in the core. They now run as a connector —
`connect::DefaultConnector` — which is the split D16 and §7.1 planned, and the reason it
matters is the sentence above: a pack cannot invent a new kind of target, and a connector
can. Every row of the table is the default connector's business:

| was | now |
|---|---|
| `protolink::link_services` called from the index pipeline | `DefaultConnector::run`, first fact it contributes |
| `deploy::parse_compose` + `link_deployment` in the same pipeline | the same connector, after the service links |
| `ondemand::scan` reached through `link_deployment` | unchanged, and now inside the connector's boundary |

The move is a move: the code still reads `rules/default.yaml`, still writes
`service_links` and the deployment tables directly, and the golden recordings are
identical to the byte. What it buys is that the pipeline no longer names any of these —
it runs the connectors it has, in manifest order, and derives afterwards. A second
connector contributing its own kinds of node and edge needs no change to the core, which
is what makes the remaining ecosystem knowledge *optional* rather than merely
configurable.

**Two things the move left behind, found by running cairn against a repository it had
never seen.** Both are the Tier 2 shape exactly — a convention compiled in, with no way
for a repository to say otherwise:

| was | now |
|---|---|
| the compose file names, a constant inside the connector | `deploy.compose_files` in the pack; a repository whose stack is in `compose.w17.yaml` says so and the whole deployment layer comes alive |
| compose `include:` ignored | followed, with each included file's own relative paths resolved from where it sits — a repository of bundles describes itself that way and cairn read half of it |
| a service with no `command:` was unresolvable | its image's `ENTRYPOINT` is its start command, which is how most containers actually start |
| the test suffix list, duplicated in `conventions.rs` | read from the pack, which is where the directory list already came from |

And one that was not Tier 2 at all but Tier 3 — a layout assumption that failed silently,
which is the class this document was opened for:

> For Go, the indexer ran at **the shallowest `go.mod` only**, on the stated grounds that
> "the outermost project sees every package inside it". That is true of a single-module
> repository and false of every workspace: Go *excludes* a nested module from its parent.
> Measured on a real monorepo — 23 modules named by `go.work`, of which one was indexed,
> and the other 22 were absent from every answer with nothing saying so. `go.work` is now
> authoritative where it exists, every `go.mod` is its own root otherwise, and
> `cairn index` prints how many projects it is about to index before it starts.

The in-process connector keeps privileged store access, and that is the one asymmetry
left: external connectors emit facts and are validated, while this one writes tables. It
is the honest position for a move rather than a rewrite, and it is written down here so
the next reader does not mistake it for the intended end state.

## Tier 3 — one genuine layout assumption, and it failed silently (fixed)

`protolink::package_of` derives the proto package by splitting the file path on `/schema/`:

```rust
let after = path.split("/schema/").nth(1)?;
```

A repository that generates protobuf code into `gen/`, `pb/`, `proto/` or anywhere else
gets **zero** cross-language links, and nothing says so — `reaches` simply reports no
callers, which is indistinguishable from a service nothing calls. That is the failure mode
the whole envelope design exists to prevent, sitting in the one mechanism the measurements
say is worth the most (tasks D and L, −34 % and −52 %).

**Both halves are now done.** The package is the directory the generated file actually sits
in, whatever it is called — `gen/go/billing_v1/…`, `pb/orders/…` and `srcpy/schema/…` all
resolve, because both generators emit `<anything>/<pkg>/…` and `<pkg>` is what the two
languages have in common. No layout name is assumed. Re-indexed against the measured
repository: still 73 services, no new phantoms.

And `cairn status` now prints the link counts, saying so in as many words when they are
zero:

```
services   0 - no cross-language links. `cairn reaches` will find nothing, and that
           is this mechanism failing, not an answer
```

## What the day's fixes did and did not do

Eight mechanisms were changed after a measurement pointed at them. Every one is a general
rule, not a special case:

* a module-level binding is a caller — `af = wrap(f)`, `const x = memoize(y)`
* an outward `calls` edge is not a parameter, a type variable or a stdlib name
* a dispatched method is attributed to its enclosing type
* a registered class puts its methods on the live path
* a blast radius runs outwards as well as inwards
* a generated-code marker belongs in the header block, not anywhere in the first 4 KB
* code a service binding reaches is dispatched, not dead
* the tool says so when it has nothing for a question

None of them names a file, a service or a domain in this repository. Each was *found*
through this repository, which is a different thing, and three of them were found only
because the target was chosen by a rule rather than by hand.
