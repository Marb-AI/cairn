# What in cairn is tied to the repository it was measured on

Written 2026-08-01, after a day of building against one codebase. The question is whether
anything was hand-fitted to that repository, and the honest answer has three tiers.

## Tier 1 — nothing names this company, repo or domain in production code

Every occurrence of a company, service, domain name, `srcpy` or
`srcgo` in the Rust source is either a doc comment recording *why* a mechanism exists, or a
test fixture. Checked by grepping all of `crates/` and separating comment and test lines
from the rest; the remainder is empty.

The constants are all generic: the handle alphabet, timeouts, `.git`/`node_modules`/`.venv`
skip lists, generated-code markers (`code generated by`, `@generated`, `do not edit`), and
protoc path hints (`.pb.go`, `_pb2.py`).

## Tier 2 — ecosystem conventions, hardcoded, and they are the load-bearing parts

These are not specific to this repository, but they are specific to *an* ecosystem, and if
a repo does not follow them the mechanism produces nothing:

| where | assumes |
|---|---|
| `deploy::resolve_command` | `python -m`, `uvicorn`/`gunicorn`, `manage.py <cmd>`, `celery -A`, `tail -f`/`sleep infinity` |
| `deploy::binary_to_package` | a Dockerfile line building with `-o <path>` |
| `deploy` Django command | a management command is a file named `<command>.py` |
| `protolink::classify` | protoc naming: `<Svc>Base`, `<Svc>Stub`, `<Svc>Client`, `<Svc>Server`, `Register<Svc>Server` |
| `ondemand` | cron's five fields, and `docker exec … -f name=<service>` |
| `conventions` | tests live in `tests/` or are named `test_*` |

Architecture D16 says the core should know no language and that these belong in a rule pack.
They are not in a rule pack. They are Rust functions in the middle of the crate, and calling
that a deliberate deferral is generous — it is a debt, and until it is paid the tool is a
Python/Go/Docker tool rather than a general one.

## Tier 3 — one genuine layout assumption, and it fails silently

`protolink::package_of` derives the proto package by splitting the file path on `/schema/`:

```rust
let after = path.split("/schema/").nth(1)?;
```

A repository that generates protobuf code into `gen/`, `pb/`, `proto/` or anywhere else
gets **zero** cross-language links, and nothing says so — `reaches` simply reports no
callers, which is indistinguishable from a service nothing calls. That is the failure mode
the whole envelope design exists to prevent, sitting in the one mechanism the measurements
say is worth the most (tasks D and L, −34 % and −52 %).

It should be inferred (the directory that generated files actually sit in) or configured,
and until then `cairn status` should say how many cross-language links were built so a zero
is visible.

## What the day's fixes did and did not do

Eight mechanisms were changed after a measurement pointed at them. Every one is a general
rule, not a special case:

* a module-level binding is a caller — `af = wrap(f)`, `const x = memoize(y)`
* an outward `calls` edge is not a parameter, a type variable or a stdlib name
* a dispatched method is attributed to its enclosing type
* a registered class puts its methods on the live path
* a blast radius runs outwards as well as inwards
* a generated-code marker belongs in the header block, not anywhere in the first 4 KB
* code a service binding reaches is dispatched, not dead
* the tool says so when it has nothing for a question

None of them names a file, a service or a domain in this repository. Each was *found*
through this repository, which is a different thing, and three of them were found only
because the target was chosen by a rule rather than by hand.
