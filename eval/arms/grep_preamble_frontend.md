# Searching a codebase with grep

`rg` (ripgrep) is installed and is the better default: it is much faster on a tree this
size, respects `.gitignore`, and skips binaries on its own. Everything below works with
`grep -rn` too where noted.

## Reach for it when

Any question that can be phrased as "where does this text appear". That is a wider class
than it sounds: identifiers, string literals, config keys, environment variables, import
lines, decorators, comments, documentation, generated code — all of it is text, and none
of it is privileged over the rest. A single pattern crosses every language and every file
type in one pass, which no language-aware tool does.

## The shape of one good search

```
rg -n "PATTERN" [PATH]              line numbers, recursive from PATH (default: here)
rg -n -w "name"                     whole word: `get` stops matching `forget`, `getter`
rg -n -F "literal.text"             fixed string: dots and brackets stop being regex
rg -n -i "pattern"                  case-insensitive
rg -n -l "pattern"                  file names only - the shape of the answer first
rg -n -c "pattern"                  count per file - which file is the centre of gravity
rg -n --type py "pattern"           only Python; --type go, --type yaml, --type md
rg -n -g '!**/schema/**' "pattern"  exclude a glob - generated trees are mostly noise
rg -n -A3 -B3 "pattern"             three lines of context each side
rg -n -U "def f\(.*\n.*bar"         multiline, for patterns that cross a line break
```

`rg -n --type-list` prints every type filter it knows.

## Start wide, then narrow — in one turn where you can

The expensive thing is not the search, it is the round trip. Several searches in one shell
command cost one round trip:

```
rg -n -l "SomeName" ; echo "=== defs ===" ; rg -n "class SomeName|def SomeName" ; \
  echo "=== callers ===" ; rg -n -w "SomeName" --type py | grep -v "/schema/"
```

A good first command usually answers "how big is this question" — `-l` or `-c` over the
whole tree — so the second one can be aimed.

## Finding a definition rather than every mention

There is no index, so a definition is found by the syntax that declares it:

```
rg -n "^\s*(class|def|async def)\s+Name\b" --type py
rg -n "^func (\([^)]*\) )?Name\b" --type go        # methods carry a receiver
rg -n "^\s*Name\s*=" --type py                     # module-level binding
rg -n "^type Name\b|^var Name\b|^const Name\b" --type go
```

If a name is declared in more than one place, all of them come back and you have to read
them to tell which is which. That is the normal case for common names.

## Callers, and why the count is usually wrong at first

`rg -n -w "name"` returns definitions, calls, imports, re-exports, tests, generated stubs
and any comment or docstring that says the word. Narrowing is the work:

```
rg -n -w "name" --type py | grep -v "^srcpy/schema/" | grep -v "_test\.py\|/tests/"
rg -n "name\s*\(" --type py            # followed by an open paren: a call, mostly
rg -n "\.name\b" --type py             # attribute or method access
rg -n "import .*\bname\b|from .* import .*\bname\b" --type py
```

Watch for these, they are where a grep-only count goes wrong:

- **Import aliases.** `from x import quota as quota_repo` means every call reads
  `quota_repo.f(...)`. Search the module alias as well as the function name.
- **Generated code.** Protobuf/gRPC trees repeat every name many times. Find them first
  (`rg -l "Code generated by\|DO NOT EDIT"`) and exclude them, or the ranking is theirs.
- **Same name, different symbol.** A handler method, a REST endpoint and a repository
  function may all be called `get_thing`. Only reading them apart tells you which is which.
- **The two sides of a network call share no identifier.** A Go client method
  `GetThing` and a Python handler `get_thing` are the same RPC in different spellings;
  neither file names the other. Bridge it through the generated artefacts or the `.proto`.
- **Dynamic dispatch.** `getattr(mod, name)`, a registry, a task queue, a Django admin
  registration. Search for the name as a *string* as well as an identifier.

## Questions about a set rather than a symbol

"What is unused", "which services are affected", "what does this package export" have no
single pattern. Build them: enumerate first, then search per item.

```
rg -n "^\s*(class|def)\s+(\w+)" -o -r '$2' --type py path/to/pkg | sort -u   # the members
# then, per name, decide whether anything outside the package mentions it
```

This is several round trips by construction. Batch the per-item searches into as few shell
commands as you can, and say in your answer that the enumeration is what it rests on.

## Deployment, config and environment

These live in ordinary files, so one search finds every use across every layer at once —
compose files, Dockerfiles, CI workflows, nginx configs, `.env` templates, Makefiles, docs:

```
rg -n "VAR_NAME"                       every occurrence, every file type, one pass
rg -n "VAR_NAME" -g '*.yaml' -g '*.yml' -g '.env*' -g 'Makefile' -g '*.conf'
```

Remember compose interpolation: `${VAR}` with no `:-default` has no fallback, so a default
declared in application code is not the same as a default the deployment will use.

## Tracing a chain by hand

"Where does this land" has no single command, so it is walked hop by hop. Each hop is the
same two questions: *what does this call*, and *who serves that*.

```
sed -n '940,960p' srcpy/.../endpoints.py          # 1. read the body you start from
rg -n "clients\.share|ShareServiceStub" srcpy/    # 2. what is the thing it calls
rg -n "class ShareService|ShareServiceServer" srcgo/ --type go   # 3. who implements it
sed -n '33,95p' srcgo/.../share.go                # 4. read that, and repeat from 2
```

Three things make this go wrong, and all three are worth checking explicitly:

- **A handler that branches has more than one landing site.** Read the whole body before
  concluding where it ends; a `switch` on a type field is two or three answers, not one.
- **The name changes spelling at a network boundary** (`get_shared_object` ↔
  `GetSharedObject`). Search both spellings at every hop.
- **A generated client and a hand-written fake implement the same interface.** The fake is
  not a hop. `rg -l "Code generated"` tells them apart.

Batch a hop's searches together; the walk is unavoidable but its round trips are not.

## Wiring: where something is registered rather than called

Framework code is reached by registration, not by a call, so searching for callers finds
nothing and that absence means nothing:

```
rg -n "include_router|add_route|APIRouter\(" --type py     # HTTP routes
rg -n "Register\w+Server|NewServer|RegisterService" --type go   # gRPC servers
rg -n "get_handlers|handlers\s*=\s*\[" --type py           # a handler list
rg -n "admin\.site\.register|@admin\.register" --type py   # Django admin
rg -n "@app\.task|@shared_task|celery" --type py           # queues
rg -n "cron|schedule|entrypoint|command:" -g '*.yaml' -g '*.sh'  # what starts it
```

If a symbol has no caller anywhere, check these before calling it dead.

## Tests are evidence, and they are also noise

`/tests/` and `*_test.go` mention names constantly. Exclude them while counting production
use, and read them when you want to know what something is *for* — a test name is often
the clearest statement of intent in the tree.

```
rg -n -w "name" --type py -g '!**/tests/**' -g '!**/test_*.py'   # production only
rg -n -w "name" -g '**/test*'                                    # only the tests
```

## Reading what you found

`sed -n '40,90p' file` reads a range; `rg -n -A20 -B5 "anchor" file` reads around an
anchor. Prefer a range over opening a 4000-line file — you already know the line number.

`rg --json` is available if you want structured output, but for reading by eye the plain
form is easier and costs less context.

## Stop when you have the answer

The cost of a run is round trips, not commands, and the way runs get expensive is
searching once more to feel sure rather than to learn something. Before another search,
say what result would change your answer. If there is none, write the answer down. Extra
depth — the next hop of a chain, the other branch of a handler — is not the same thing as
asking the question you already answered a second way; do the first, skip the second.
